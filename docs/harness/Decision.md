# Decision — 사람 판단 규칙

루프 중에 에이전트가 **사람에게 판단을 묻는 순간**의 규칙을 정한다.
무엇을, 어디서, 어떤 양식으로 묻고, 무엇을 사람의 답으로 인정하는지가 이 문서의 범위다.

---

## 1. 범위

### 결정 지점

| 지점 | 언제 ([Loop](Loop.md) 상태) | 어디서 | 사람의 답 (결과값) |
|---|---|---|---|
| **D1 NEEDS_HUMAN** | 3.1절의 사유가 생겼을 때 | Issue | 결정 · 상한 · 재개/중단 |
| **D2 PR 진입** | `로컬 통과`이고 PR이 아직 없을 때 | Issue | AI / 사람 |
| **D3 최종 판정** | `승인 대기` (CI 통과 뒤) | PR | 승인/반려 · 상한 · 요청 내용 |

### Loop와의 경계

| 이 문서 (Decision) | [Loop.md](Loop.md) |
|---|---|
| 언제 사람에게 묻는가 (사유와 분류) | 그때 루프를 멈추고 상태를 기록하는 것 |
| 요청 코멘트와 응답 양식 | 시도 횟수 (`NEEDS_HUMAN`의 셈, 반려 +1 포함) |
| 무엇을 사람의 답으로 인정하는가 | 결과값에 따른 상태 전이와 그 뒤의 절차 (재개, PR 생성, 재작업 등) |

---

## 2. 공통 원칙

### 2.1 사람은 양식을 찾아보지 않는다

**사람은 이 문서나 양식을 찾아보지 않는다고 가정한다.** 그래서 에이전트는 판단을 요청할 때 사람이 채울 양식을 **요청 안에 직접 붙여서** 준다.

- 양식의 선택지와 기본값은 에이전트가 이번 상황에 맞게 미리 채운다. 사람은 고르고 붙여 넣기만 하면 된다.
- 양식은 복사하기 쉽게 코드 블록으로 감싼다.
- 대화 중이면 사용자에게도 **같은 내용과 같은 양식**을 준다. 사용자는 대화로 답해도 된다 (2.3절).

### 2.2 사람이 작성하는 코멘트

에이전트의 루프 기록(`<!-- loop-record -->`)과 달리, 아래 코멘트는 **사람이 작성한다.**

| 양식 | 첫 줄 표지 | 남기는 곳 | 지점 |
|---|---|---|---|
| NEEDS_HUMAN 응답 | `<!-- loop-decision -->` | Issue | D1 |
| PR 진입 응답 | `<!-- loop-decision -->` | Issue | D2 |
| 최종 판정 | `<!-- loop-review -->` | PR | D3 |

- 에이전트는 이 코멘트를 스스로 작성하지 않는다. 사람의 판단 없이 답을 만들어 진행하지 않는다.
- 예외는 하나다. 사람이 양식 없이 답했거나 대화로만 답한 내용을 에이전트가 **옮겨 적는** 경우다 (2.3절). 이때는 메모에 옮겨 적었다는 사실과 원문 위치를 남긴다.

### 2.3 양식 없이 받은 답, 대화로 받은 답

- 판단이 분명하면 에이전트가 그 내용을 해당 양식으로 옮겨, 그 지점의 자리(Issue 또는 PR)에 남긴 뒤 진행한다. 메모에 `에이전트가 옮겨 적음 — 원문: <코멘트 링크 또는 대화>`를 적는다.
- 분명하지 않으면 진행하지 않는다. 무엇이 불분명한지 적고 양식을 다시 준다.
- Issue나 PR에 남지 않은 판단으로는 진행하지 않는다.

### 2.4 답이 없을 때

- 답이 올 때까지 아무것도 하지 않고 기다린다. 기한을 두고 스스로 진행하지 않는다.
- 세션이 바뀌어 다시 확인했는데 여전히 답이 없으면, 대기 중이라는 사실과 양식을 사용자에게 다시 준다.

---

## 3. D1 NEEDS_HUMAN

선언과 응답은 PR이 생긴 뒤에도 **Issue에서** 한다.

### 3.1 선언하는 경우

`NEEDS_HUMAN`은 두 종류다.

- **판단형** — Issue나 원본 문서만으로는 에이전트가 정할 수 없어 사람의 판단이 필요한 경우.
- **실패형** — 실패가 쌓였거나 원인을 알 수 없는 실패가 나서 멈추는 경우.

| 경우 | 분류 | 근거 |
|---|---|---|
| Issue와 SSOT(도메인·아키텍처 원본)가 충돌한다 | 판단형 | [SSOT](SSOT.md) 3절 |
| SSOT끼리 충돌한다 | 판단형 | [SSOT](SSOT.md) 3절 |
| 통과하려면 검증 규칙·스크립트를 바꿔야 한다 | 판단형 | [VerifyRule](VerifyRule.md) 7절 |
| AI에게 읽기만 허용된 영역을 바꿔야 한다 | 판단형 | [SSOT](SSOT.md) 4절 |
| Issue만으로 구현 방향을 하나로 정할 수 없다 (업무 판단이 갈린다) | 판단형 | 이 문서 |
| 복구할 때 루프 기록과 작업 트리 · 브랜치 · PR이 맞지 않는다 | 판단형 | [Loop](Loop.md) 7절 |
| 상한에 도달했는데 통과하지 못했다 | 실패형 | [Loop](Loop.md) 3절 · 6.5절 |
| 로컬에서 통과한 커밋이 CI에서 실패했다 | 실패형 | [Loop](Loop.md) 6.4절 |

분류에 따른 시도 횟수의 셈은 [Loop](Loop.md) 2절이 정한다.

### 3.2 선언할 때 하는 일 — 도움 요청 코멘트

1. **즉시 멈춘다.** 코드를 더 바꾸지 않고, `npm run verify`도 더 돌리지 않고, 커밋 · 푸시도 하지 않는다.
2. Issue에 상태 `NEEDS_HUMAN`으로 루프 기록을 남긴다. 기본 필드([Loop](Loop.md) 4절)에 아래를 덧붙이고, 맨 끝에 **응답 양식**(3.3절)을 붙인다.
   - 분류, 사유, 근거(문서 위치), 선택지, 에이전트 의견(선택)
3. 시도 횟수는 [Loop](Loop.md) 2절의 셈대로 기록한다. 기록한 시도가 상한과 같아 남은 횟수가 없으면, 응답 양식의 `상한` 칸에 새 값을 제안해 미리 채운다.

예시 — 시작 점검에서 남기는 도움 요청 코멘트:

````markdown
<!-- loop-record -->
**Loop 기록**

- 상태: NEEDS_HUMAN
- 시도: 0 / 3 (시작 점검이라 세지 않음)
- 마지막 검증: 없음
- 분류: 판단형
- 사유: Issue ↔ SSOT 충돌
- 근거: Issue #3 "2. 변경할 내용" ↔ docs/06-architecture.md §4.2 "만료된 로트도 후보에 포함한다"
- 선택지:
  1. 출고 요청 전체를 거부한다 (배분 로직은 그대로)
  2. 7일 미만 로트를 배분에서 제외한다 (풀필먼트·팝업과 공유하는 배분 함수를 바꿔야 함)
- 에이전트 의견: 1안 — Issue "5. 건드리면 안 되는 것"과 겹치지 않는다
- 다음 할 일: 사람의 응답을 기다린다

**아래 양식을 복사해 이 Issue에 코멘트로 남겨 주세요.**

```markdown
<!-- loop-decision -->
**NEEDS_HUMAN 응답 (사람 작성)**

- 결정: 1   ← 1 / 2 / 직접 입력
- 상한: 그대로   ← 그대로 / 새 값(예: 5)
- 재개: 재개   ← 재개 / 중단
- 메모:
```
````

### 3.3 응답 양식

```markdown
<!-- loop-decision -->
**NEEDS_HUMAN 응답 (사람 작성)**

- 결정: (선택지 번호 또는 직접 입력)
- 상한: 그대로 | 새 값
- 재개: 재개 | 중단
- 메모: (선택)
```

| 필드 | 규칙 |
|---|---|
| 결정 | 요청 코멘트의 선택지 번호. 선택지에 없는 판단이면 문장으로 적는다 |
| 상한 | 바꾸지 않으면 `그대로`. 새 값을 적으면 그 값이 새 상한이 된다 |
| 재개 | `재개`면 에이전트가 이어서 진행한다. `중단`이면 루프를 끝낸다 |
| 메모 | 에이전트가 알아야 할 추가 지시 |

사유별로 에이전트가 미리 채우는 선택지의 기본형:

| 사유 | 기본 선택지 |
|---|---|
| Issue ↔ SSOT, SSOT ↔ SSOT 충돌 | 따를 쪽(각 선택지) / 사람이 원본을 고친 뒤 재개 |
| 검증 규칙·보호 영역을 바꿔야 함 | 사람이 직접 고친 뒤 재개 / 바꾸지 않는 다른 방법을 찾는다 / 중단 |
| Issue만으로 방향을 정할 수 없음 | 에이전트가 찾은 구현 방향들 |
| 복구 불일치 | 현재 작업 트리 · 브랜치를 기준으로 이어간다 / 사람이 정리한 뒤 재개 / 중단 |
| 상한 도달 | 상한을 올려 재개 / 중단 |
| CI 실패 (로컬은 통과) | 사람이 원인을 고친 뒤 CI를 다시 확인 / 에이전트가 코드를 고친다 (메모에 지시) / 중단 |

### 3.4 답으로 인정하는 것

- `NEEDS_HUMAN` 기록 **뒤에** 달린 NEEDS_HUMAN 응답만 인정한다. 양식 없이 받은 답은 2.3절을 따른다.
- 범위나 종료 조건이 바뀌는 판단이면 Issue 본문을 먼저 고친 뒤 진행한다 ([SSOT](SSOT.md) 2절).
- 상한을 바꾼 응답이면 그 값을 새 상한으로 쓴다. 시도 횟수는 0으로 되돌리지 않는다.
- 남은 횟수가 없는데(시도 = 상한) 상한이 `그대로`인 `재개`는 인정하지 않는다. 상한을 올려 달라고 응답 양식을 다시 준다.
- 결과값(`재개` · `중단`)에 따른 다음 절차는 [Loop](Loop.md) 5절을 따른다.

## 4. D2 PR 진입

로컬 검증을 통과한 뒤 사람이 정하는 것은 **PR을 에이전트가 열지, 사람이 직접 열지**뿐이다. 결과물에 대한 승인 · 반려는 CI를 통과한 뒤 D3에서 받는다.

- **묻는 때:** `로컬 통과`이고 그 브랜치에 PR이 아직 없을 때. PR이 이미 있으면 묻지 않는다.
- **묻는 곳:** Issue. `로컬 통과` 루프 기록 끝에 아래 양식을 붙인다.
- 이 요청은 `NEEDS_HUMAN`이 아니다.

```markdown
<!-- loop-decision -->
**PR 진입 응답 (사람 작성)**

- 진행: AI   ← AI / 사람
- 메모:
```

| 결과값 | 뜻 |
|---|---|
| AI | 에이전트가 커밋 · 푸시 · PR을 만든다 |
| 사람 | 사람이 직접 커밋 · 푸시 · PR을 만든다 |

결과값에 따른 다음 절차는 [Loop](Loop.md) 6.2절을 따른다.

## 5. D3 최종 판정

CI를 통과한 결과물을 받아들일지는 **사람이 PR 코멘트로** 정한다.
PR을 만든 계정은 GitHub 리뷰(Approve · Request changes)를 남길 수 없다. 에이전트도 사용자 계정으로 PR을 만들기 때문에, 판정은 리뷰 버튼이 아니라 코멘트 양식으로 받는다.

### 5.1 승인 요청 — 에이전트의 PR 코멘트

CI 통과를 확인하면 PR에 아래 코멘트를 남긴다.

````markdown
<!-- loop-approval-request -->
**최종 판정 요청**

- Issue: #3
- 커밋: 3f5aefd (이 커밋에 대한 판정만 유효)
- CI: 통과 · <링크>
- 시도: 2 / 3

**아래 양식을 복사해 이 PR에 코멘트로 남겨 주세요.**

```markdown
<!-- loop-review -->
**최종 판정 (사람 작성)**

- 판정: 승인   ← 승인 / 반려
- 요청 내용: (반려일 때 무엇을 고칠지)
- 상한: 그대로   ← 그대로 / 새 값
- 메모:
```
````

- 반려 한 번은 시도를 최소 2회 쓴다 ([Loop](Loop.md) 2절). 그래서 남은 횟수(상한 − 시도)가 2보다 적으면 `상한` 칸에 새 값을 제안해 미리 채운다.

### 5.2 판정 양식

| 필드 | 규칙 |
|---|---|
| 판정 | `승인` 또는 `반려` |
| 요청 내용 | 반려일 때 무엇을 고칠지. 승인이면 비워 둔다 |
| 상한 | 바꾸지 않으면 `그대로`. 새 값을 적으면 그 값이 새 상한이 된다 |
| 메모 | 에이전트가 알아야 할 추가 지시 |

### 5.3 판정으로 인정하는 것

- 승인 요청 코멘트 **이후에** 달린 `<!-- loop-review -->` 코멘트만 판정으로 본다. 승인 요청 전, CI 통과 전에 달린 PR 코멘트는 판정으로 보지 않는다. 양식 없이 받은 답은 2.3절을 따른다.
- 판정은 승인 요청에 적힌 커밋에 대해서만 유효하다. 그 뒤에 새 커밋이 올라가면 이전 판정은 효력이 없고, CI 통과 뒤 승인 요청을 다시 남긴다.
- 결과값(`승인` · `반려`)에 따른 다음 절차는 [Loop](Loop.md) 6.5절을 따른다.
