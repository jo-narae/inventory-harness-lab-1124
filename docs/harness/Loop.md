# Loop — 루프 규칙

Issue 작업 하나를 **시작해서 PR에서 최종 승인을 받거나 멈출 때까지** 에이전트가 따르는 절차를 정한다.
세션이 끊기거나 바뀌어도 같은 지점에서 이어갈 수 있게 하는 것이 목적이다.

---

## 1. 범위

| 다룬다 | 다루지 않는다 (이 문서 밖) |
|---|---|
| 작업 시작 점검 | 사람에게 묻는 방법과 답의 인정 → [Decision.md](Decision.md) |
| 시도 횟수와 상한 | 머지 (사람이 한다) |
| Issue 코멘트로 남기는 루프 기록 | `main`과의 충돌 해소 |
| 사람 판단 지점에서 멈추고, 답에 따라 상태를 바꾸는 것 (5절) | 머지 뒤 `main` push CI |
| 브랜치 · 커밋 · 푸시 · PR 생성 (최소 규칙, 6.1절) | Issue 닫기, 종료 조건 체크박스 처리 |
| PR · CI 진입과 복귀, 반려 뒤 재작업 | 판정 테스트의 승인 · 보호 절차 |
| 세션이 바뀌었을 때 복구 | 작업 공간 정리 |

통과 기준과 검증 단계, CI가 무엇을 실행하는지는 [`VerifyRule.md`](VerifyRule.md)를 따른다. 이 문서는 그 기준을 **몇 번까지, 어떻게 기록하며** 돌리는지와 **언제 PR · CI로 넘어가고 돌아오는지**만 정한다.

### 기록 위치

| 위치 | 담는 것 |
|---|---|
| **Issue** | 작업의 원본과 루프 추적 — 루프 기록, 시도 횟수, `NEEDS_HUMAN`과 그 응답, PR 진입 응답 |
| **PR** | CI를 통과한 결과물에 대한 사람의 최종 판정 — 승인 요청과 승인 · 반려 |

PR의 판정 결과도 Issue 루프 기록에 남기고 PR 코멘트 링크를 붙인다. Issue만 읽어도 루프 전체를 따라갈 수 있어야 한다.

브랜치 규칙은 당분간 이 문서에 둔다. 문서가 복잡해지면 별도 SSOT로 나눈다.

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 시도 | 아래 "시도로 세는 것" 표에서 **+1**로 정한 사건 |
| 상한 | 해당 Issue "6. 구현 루프 최대 횟수"의 값. 사람이 D1 응답이나 D3 판정([Decision](Decision.md))에서 상한을 바꿨으면 가장 최근 값. **로컬 검증과 CI가 함께 쓴다** |
| 반려 | D3 최종 판정에서 사람이 결과물을 받아들이지 않은 것 |
| 재작업 | 반려된 뒤 다시 구현에 들어가는 것. **반려 = 재작업 돌입이며, +1은 한 번만 붙는다** |
| 재진입 | 멈췄던 루프를 이어가는 것. `NEEDS_HUMAN` 응답을 받아 **재개**하거나, 세션이 바뀌어 **복구**하는 것. 재작업은 재진입이 아니다 |
| 루프 기록 | 에이전트가 Issue에 남기는 코멘트 (4절 형식) |
| 현재 상태 | 그 Issue의 **가장 최근** 루프 기록 |

### 상태

| 상태 | 뜻 |
|---|---|
| `진행 중` | 로컬 루프에서 구현 · 검증 중 |
| `로컬 통과` | 로컬 `npm run verify` exit 0. PR이 없으면 D2 답을 기다린다 |
| `CI 대기` | PR의 CI 결과를 기다린다 (6.3절) |
| `승인 대기` | CI를 통과했고, D3 최종 판정을 기다린다 |
| `승인` | 사람이 PR에서 승인했다. **루프가 끝나고** 머지를 기다린다 |
| `NEEDS_HUMAN` | D1 응답을 기다린다 |
| `중단` | 사람이 중단을 정했다 |

### 시도로 세는 것 / 세지 않는 것

**`NEEDS_HUMAN` 선언 자체는 세지 않는다.** 선언의 원인이 되는 사건만 센다.

| 사건 | 셈 |
|---|---|
| 로컬에서 `npm run verify`가 끝나고 exit code를 확인했다 (0이든 아니든) | **+1** |
| PR의 CI가 실패했다 | **+1** |
| D3에서 반려됐다 (재작업 돌입) | **+1** |
| 루프 중에 판단형 `NEEDS_HUMAN` 사유가 생겼다 | **+1** |
| 반려 때문에 Issue 본문을 고쳤다 | 0 — 같은 반려에 딸린 일이다 |
| 시작 점검에서 판단형 `NEEDS_HUMAN` 사유가 생겼다 | 0 |
| 실패형 `NEEDS_HUMAN`을 선언했다 (상한 도달, CI 실패) | 0 — 원인이 된 실패를 이미 셌다 |
| 재진입했다 (재개, 복구) | 0 |
| 복구할 때 기록이 맞지 않아 `NEEDS_HUMAN`을 선언했다 | 0 — 재진입 시점이다 |
| D2 요청, CI 통과, D3 승인 요청, 승인 | 0 |
| 단계 하나만 따로 실행했다 (`vitest run`, `npm run lint` 등) | 0. 판정에도 쓰지 않는다 |
| 명령을 잘못 써서, 또는 중간에 끊겨서 exit code를 확인하지 못했다 | 0. 다시 실행한다 |

`NEEDS_HUMAN`의 사유와 판단형 · 실패형 분류는 [Decision](Decision.md) 3.1절을 따른다.

반려 한 번은 반려(+1)와 그 뒤의 로컬 검증(+1)으로 **최소 2회**를 쓴다.

## 3. 루프 절차

```
시작 점검 ──걸림──▶ D1 NEEDS_HUMAN (0)
    │ 통과
    ▼
브랜치 ─▶ 시작 기록 ─▶ ┌──────────── 로컬 루프 ────────────┐
                       │ 구현 ─▶ npm run verify ─▶ 시도 기록(+1)
                       │  ▲                          │
                       │  └──── 실패, n < 상한 ──────┤
                       └─────────────────────────────┼──────┘
                                                     ├─ 실패, n = 상한 ─▶ D1 NEEDS_HUMAN (0, 상한 도달)
                                                     ▼ exit 0
                                                 로컬 통과 ─▶ D2 PR 진입 (AI / 사람)   [Issue]
                                                                 │
                                                                 ▼
                                                             CI 대기
                                                   ┌─────────────┴─────────────┐
                                             CI 실패(+1)                    CI 통과
                                                   │                           │
                                                   ▼                           ▼
                                      D1 NEEDS_HUMAN (0, CI 실패)    승인 대기 ─▶ D3 최종 판정   [PR]
                                                                               │
                                                                 ┌─────────────┴─────────────┐
                                                                승인                      반려(+1)
                                                                 │                           │
                                                                 ▼                           │
                                                         루프 종료 · 머지는 사람             │
                                                                                             │
                           구현으로 복귀 (같은 브랜치 · 시작 점검 안 함) ◀───────────────────┘
```

1. **시작 점검.** Issue당 **처음 한 번만** 한다 (루프 기록이 없을 때). Issue를 읽고 판단형 `NEEDS_HUMAN` 사유([Decision](Decision.md) 3.1절)에 해당하는지 본다. 해당하면 구현하지 않고 D1을 선언한다. 시작 점검에서는 세지 않는다 (`0/상한`).
   - 재진입(재개 · 복구)과 재작업 때는 시작 점검을 다시 하지 않는다.
2. **브랜치.** 6.1절대로 작업 브랜치를 만든다.
3. **시작 기록.** 코드를 바꾸기 전에 루프 기록(상태 `진행 중`, 시도 `0/상한`)을 남긴다.
   이미 루프 기록이 있으면 새로 시작하지 않고 7절(복구)을 따른다.
4. **구현.**
5. **검증.** `npm run verify`를 실행한다.
6. **시도 기록.** 결과와 상관없이 매 시도 직후 루프 기록을 남긴다 (+1).
7. **판정.**
   - exit 0 → 상태 `로컬 통과`로 기록한다. PR이 없으면 D2를 요청한다 (6.2절).
   - 실패, 시도 < 상한 → 4로 돌아간다.
   - 실패, 시도 = 상한 → 상한 도달로 D1을 선언한다 (실패형, 0).
8. 루프 중 언제든 판단형 `NEEDS_HUMAN` 사유가 생기면 그 자리에서 멈추고 D1을 선언한다 (+1).

**PR · CI로는 로컬 `npm run verify`가 exit 0일 때만 들어간다.** 로컬에서 통과하지 않은 코드를 커밋 · 푸시해 CI로 확인하지 않는다.

## 4. 루프 기록 — Issue 코멘트

루프의 상태는 **해당 Issue의 코멘트로만** 남긴다. 대화나 로컬 파일에 남긴 것은 기록으로 치지 않는다. PR에서 일어난 일(승인 요청, 판정)도 Issue 루프 기록에 옮겨 남긴다.

### 언제 남기는가

| 시점 | 상태 |
|---|---|
| 시작할 때 (코드 변경 전) | `진행 중` |
| 매 로컬 시도 직후 | `진행 중` 또는 `로컬 통과` |
| PR이 생기고 CI가 시작됐을 때 (재푸시 포함) | `CI 대기` |
| CI 실패를 확인했을 때 | `NEEDS_HUMAN` |
| CI 통과를 확인하고 PR에 승인 요청을 남겼을 때 | `승인 대기` |
| PR에서 승인을 확인했을 때 | `승인` |
| PR에서 반려를 확인했을 때 (재작업 돌입) | `진행 중` |
| 멈출 때 | `NEEDS_HUMAN` |
| 사람의 판단을 받아 다시 시작할 때 | `진행 중` |
| 사람이 중단을 정했을 때 | `중단` |

- 이전 코멘트를 고치지 않는다. 항상 새 코멘트를 덧붙인다.
- 상한은 매 기록에 다시 적는다. 이전 기록을 찾아보지 않아도 남은 횟수를 알 수 있어야 한다.

### 형식

첫 줄의 `<!-- loop-record -->`로 루프 기록을 다른 코멘트와 구분한다.

```markdown
<!-- loop-record -->
**Loop 기록**

- 상태: 승인 대기
- 시도: 2 / 3
- 마지막 검증: CI 통과
- 이번 시도에서 바꾼 것: src/actions/outbound.ts 검사 위치를 applyMovement 앞으로 이동
- 브랜치: issue-3-expired-product-outbound
- PR: #7
- 커밋: 3f5aefd
- CI: https://github.com/<owner>/<repo>/actions/runs/<id>
- PR 판정: 승인 요청 <코멘트 링크>
- 다음 할 일: PR 최종 판정 확인
```

| 필드 | 규칙 |
|---|---|
| 상태 | 2절 상태 중 하나 |
| 시도 | `n / 상한`. 시작 기록은 `0 / 상한` |
| 마지막 검증 | 어디서(로컬 · CI) 돌렸는지, exit code, 실패 단계 이름 ([VerifyRule](VerifyRule.md) 1절의 단계명). 시작 기록은 `없음` |
| 실패 요약 | 에러 출력에서 원인이 드러나는 부분. 통과면 생략 |
| 이번 시도에서 바꾼 것 | 파일과 변경 요지 |
| 브랜치 | 작업 브랜치 이름 (6.1절) |
| PR | PR 번호. PR이 생긴 뒤부터 적는다 |
| 커밋 | PR의 최신 커밋 SHA. 푸시한 뒤부터 적는다 |
| CI | CI 실행 링크. CI가 시작된 뒤부터 적는다 |
| PR 판정 | 승인 요청 · 승인 · 반려 중 무엇인지와 그 PR 코멘트 링크. 반려면 요청 내용 요약도 적는다. 승인 요청을 남긴 뒤부터 적는다 |
| 다음 할 일 | 다음 세션이 그대로 이어받을 수 있는 한 줄 |

`NEEDS_HUMAN` 기록에 덧붙이는 필드(분류, 사유, 근거, 선택지, 응답 양식)는 [Decision](Decision.md) 3.2절을 따른다.

## 5. 사람 판단 지점

루프는 아래 지점에서 멈추고 사람의 답을 기다린다. **무엇을 어떻게 묻고 무엇을 답으로 인정하는지**는 [Decision.md](Decision.md)가 정한다. 이 절은 **멈추는 때와, 답에 따라 루프가 하는 일**만 정한다.

| 지점 | 멈추는 때 | 셈 | 답에 따른 루프의 처리 |
|---|---|---|---|
| **D1 NEEDS_HUMAN** | 3절 1 · 7 · 8단계, 6.4절, 6.5절, 7절 | 2절 표대로 | `재개` → 상태 `진행 중`으로 기록하고 이어간다 (재진입, 0, 시작 점검 안 함). `중단` → 상태 `중단`으로 기록하고 끝낸다 |
| **D2 PR 진입** | `로컬 통과`이고 PR이 없을 때 | 0 | 6.2절 |
| **D3 최종 판정** | `승인 대기` | 승인 0 · 반려 +1 | 6.5절 |

- 멈춰 있는 동안에는 코드를 바꾸지 않고, `npm run verify`를 돌리지 않고, 커밋 · 푸시도 하지 않는다.
- D1 · D3의 답에 새 상한이 있으면 루프는 그 값을 상한으로 쓴다. 시도 횟수는 0으로 되돌리지 않는다.
- 재개할 때 근거가 된 응답을 루프 기록에 적는다.

## 6. PR · CI

### 6.1 브랜치 · 커밋 · 푸시 (최소 규칙)

| 항목 | 규칙 |
|---|---|
| 브랜치 이름 | `issue-{Issue 번호}-{기능명}`. 기능명은 판정 테스트 파일(`tests/issues/issue-{번호}-{기능명}.test.ts`)과 같게 쓴다 |
| 만드는 시점 | 시작 기록 전, 코드를 바꾸기 전. 최신 `main`에서 만든다 |
| 이미 있으면 | 새로 만들지 않고 그 브랜치에서 이어간다 (7절) |
| 작업 위치 | `main`에서 직접 작업 · 커밋 · 푸시하지 않는다 |
| 커밋 · 푸시 시점 | `로컬 통과` 상태에서만. 처음 PR은 D2 답대로, PR이 생긴 뒤의 재푸시는 묻지 않고 에이전트가 한다 |
| PR | base `main`, 제목은 Issue 제목, 본문에 `Refs #{Issue 번호}`. `Closes` · `Fixes`는 쓰지 않는다 (Issue 닫기는 범위 밖) |
| 하지 않는 것 | force push, 푸시한 커밋 고쳐 쓰기(amend · rebase), 머지, PR 닫기 |

### 6.2 PR 진입

1. `로컬 통과`이고 PR이 없으면 D2를 요청하고 멈춘다 ([Decision](Decision.md) 4절).
2. D2 답에 따라:
   - **AI** → 에이전트가 커밋 · 푸시 · PR 생성 (6.1절) → 상태 `CI 대기`로 기록한다.
   - **사람** → 사람이 직접 커밋 · 푸시 · PR을 만든다. 에이전트는 그 브랜치에 PR이 생겼는지(`gh pr list --head <브랜치>`) 확인한 뒤 PR 번호 · 커밋 SHA를 적어 `CI 대기`로 기록한다.
- PR이 이미 있는 상태에서 다시 `로컬 통과`가 되면 D2를 묻지 않는다. 에이전트가 같은 브랜치에 커밋 · 푸시하고 `CI 대기`로 기록한다.

### 6.3 CI 대기

- `CI 대기`로 기록할 때 PR 번호, PR의 최신 커밋 SHA, CI 실행 링크를 적는다.
- 세션 안에서는 `gh pr checks <PR 번호> --watch`로 결과를 기다린다.
- 세션이 끝나도 괜찮다. 다음 세션이 7절대로 CI 결과를 확인해 이어간다.
- CI 결과는 **기록한 커밋 SHA에 대한 것**만 인정한다. PR의 최신 커밋(`gh pr view <PR 번호> --json headRefOid`)이 기록과 다르면 복구 불일치로 본다 (7절).

### 6.4 CI 결과

| 결과 | 셈 | 처리 |
|---|---|---|
| CI 통과 | 0 | D3 승인 요청을 PR에 남기고([Decision](Decision.md) 5.1절) 상태 `승인 대기`로 기록한다 |
| CI 실패 | **+1** | 실패형 D1(CI 실패)을 Issue에 선언한다 (선언은 0). 실패 단계와 CI 로그 요약을 적는다 |

- 로컬에서 통과한 커밋만 CI로 가므로, CI 실패는 로컬과 CI의 차이로 본다. 에이전트는 원인을 추측해서 고치지 않고 사람에게 판단을 요청한다. CI 워크플로는 보호 영역이다 ([VerifyRule](VerifyRule.md) 7절).

### 6.5 최종 판정 뒤 — 승인 · 반려

D3 답(판정)에 따라 처리한다. 판정으로 인정하는 조건은 [Decision](Decision.md) 5.3절을 따른다.

| 판정 | 셈 | 처리 |
|---|---|---|
| 승인 | 0 | Issue에 상태 `승인`으로 기록한다 (PR 판정 필드에 판정 코멘트 링크). **루프가 끝난다.** 머지는 사람이 한다 |
| 반려 | **+1** | 재작업에 들어간다 (아래) |

**반려 — 재작업**

1. 판정의 `상한` 칸에 새 값이 있으면 먼저 적용한다.
2. 범위나 종료 조건이 바뀌는 요청이면 Issue 본문을 먼저 고친다 ([SSOT](SSOT.md) 2절). 이 수정은 따로 세지 않는다.
3. **시도를 1 올려** Issue에 상태 `진행 중`으로 루프 기록을 남긴다. PR 판정 필드에 판정 코멘트 링크와 요청 내용 요약을 적는다. 요청 원문은 PR 코멘트이며 Issue로 옮겨 적지 않는다.
4. 같은 브랜치에서 로컬 루프로 돌아간다 (3절 4단계). 시작 점검은 다시 하지 않는다.
5. 다시 `로컬 통과`가 되면 묻지 않고 재푸시하고(6.2절 마지막 항목) `CI 대기` → `승인 대기` → 새 승인 요청으로 이어간다.

- 반려로 시도가 상한에 닿으면 로컬 검증을 할 수 없다. 곧바로 실패형 D1(상한 도달)을 Issue에 선언한다 (0).

## 7. 세션이 바뀌었을 때 복구

복구는 재진입이다. 시작 점검을 다시 하지 않고, 시도로 세지 않는다.

1. Issue 본문과 코멘트를 읽는다 — `gh issue view <번호> --repo jo-narae/inventory-harness-lab-1124 --comments`
2. `<!-- loop-record -->`가 있는 코멘트 중 **가장 최근 것**을 현재 상태로 삼는다. 그 뒤에 달린 `<!-- loop-decision -->` 응답도 함께 읽는다.
3. 기록에 PR이 있으면 PR 코멘트와 CI 결과도 읽는다 — `gh pr view <PR 번호> --comments`, `gh pr checks <PR 번호>`. 가장 최근 `<!-- loop-approval-request -->`와 그 뒤의 `<!-- loop-review -->`를 찾는다.

| 현재 상태 | 할 일 |
|---|---|
| 기록 없음 | 처음부터 시작한다 (3절 1단계) |
| `진행 중` | 기록된 시도 횟수에서 이어간다. "다음 할 일"부터 시작한다 |
| `로컬 통과` | D2 답이 있으면 6.2절대로 진행한다. `사람`이면 그 브랜치에 PR이 생겼는지 확인한다. 답이 없으면 대기한다 ([Decision](Decision.md) 2.4절) |
| `CI 대기` | CI 결과를 확인해 6.4절대로 처리한다. 아직 돌고 있으면 기다린다 |
| `승인 대기` | 승인 요청 뒤에 판정이 있으면 6.5절대로 처리한다. 없으면 대기한다 ([Decision](Decision.md) 2.4절) |
| `승인` | 루프를 다시 돌리지 않는다. 머지 대기라고 알린다 |
| `NEEDS_HUMAN` | 그 뒤에 D1 응답이 있으면 5절대로 처리한다. 없으면 대기한다 ([Decision](Decision.md) 2.4절) |
| `중단` | 루프를 다시 돌리지 않는다. 사람이 중단했다고 알린다 |

4. 작업 위치를 확인한다. 기록에 브랜치가 있으면 그 브랜치로 전환한다. 아래 중 하나라도 맞지 않으면 추측해서 맞추지 않고 D1(복구 불일치)을 선언한다. 재진입 시점이므로 세지 않는다 (0).
   - 기록의 브랜치가 없다
   - 작업 트리가 기록의 "이번 시도에서 바꾼 것"과 맞지 않는다
   - 기록에 커밋이 있는데 브랜치 · PR의 최신 커밋이 그것과 다르다

- 시도 횟수는 세션이 바뀌어도 초기화하지 않는다. Issue에 남은 기록이 유일한 근거다.
- 루프 기록 없이 진행한 시도는 복구할 수 없다. 그래서 4절의 "언제 남기는가"를 건너뛰지 않는다.
