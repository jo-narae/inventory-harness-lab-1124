# Loop — 루프 규칙

Issue 작업 하나를 **시작해서 로컬 검증을 통과하거나 멈출 때까지** 에이전트가 따르는 절차를 정한다.
세션이 끊기거나 바뀌어도 같은 지점에서 이어갈 수 있게 하는 것이 목적이다.

---

## 1. 범위

| 다룬다 | 다루지 않는다 (이 문서 밖) |
|---|---|
| 작업 시작 점검 | 커밋 · 푸시 · PR · CI |
| 시도 횟수와 상한 | 브랜치 전략, 작업 공간 정리 |
| Issue 코멘트로 남기는 루프 기록 | Issue 닫기, 종료 조건 체크박스 처리 |
| 세션이 바뀌었을 때 복구 | 판정 테스트의 승인 · 보호 절차 |
| `NEEDS_HUMAN` 선언, 사람의 응답 양식, 재개 | |

통과 기준과 검증 단계는 [`VerifyRule.md`](VerifyRule.md)를 따른다. 이 문서는 그 기준을 **몇 번까지, 어떻게 기록하며** 돌리는지만 정한다.

---

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 시도 | `npm run verify`를 끝까지 실행해 **exit code를 확인한 것** 1회, 또는 **`NEEDS_HUMAN` 선언** 1회 (실패로 본다) |
| 상한 | 해당 Issue "6. 구현 루프 최대 횟수"의 값. 사람이 응답(5.3절)에서 상한을 바꿨으면 가장 최근 응답의 값 |
| 루프 기록 | 에이전트가 Issue에 남기는 코멘트 (4절 형식) |
| 현재 상태 | 그 Issue의 **가장 최근** 루프 기록 |

### 시도로 세는 것 / 세지 않는 것

| 경우 | 셈 |
|---|---|
| `npm run verify`가 끝나고 exit code를 확인했다 (0이든 아니든) | **1회** |
| 단계 하나만 따로 실행했다 (`vitest run`, `npm run lint` 등) | 세지 않는다. 판정에도 쓰지 않는다 |
| 명령을 잘못 써서, 또는 중간에 끊겨서 exit code를 확인하지 못했다 | 세지 않는다. 다시 실행한다 |
| `NEEDS_HUMAN`을 선언했다 (시작 점검 · 루프 중 · 복구 시 모두) | **1회 (실패)** |
| 직전 `npm run verify` 실패를 이유로 곧바로 `NEEDS_HUMAN`을 선언했다 (상한 도달 포함) | 그 verify 실패와 같은 시도로 본다. 한 번의 실패를 두 번 세지 않는다 |

## 3. 루프 절차

```
시작 점검 ─▶ 시작 기록(0/상한) ─▶ 구현 ─▶ npm run verify ─▶ 시도 기록(n/상한)
                │                              ▲                │
                ▼                              │      exit 0 ───┼──▶ 통과 (종료)
      NEEDS_HUMAN(+1 실패)                     └──── n < 상한 ──┤
                                                    n = 상한 ───┴──▶ NEEDS_HUMAN (상한 도달)
```

1. **시작 점검.** Issue를 읽고 5.1절의 `NEEDS_HUMAN` 조건에 해당하는지 먼저 본다. 해당하면 구현하지 않고 `NEEDS_HUMAN`을 선언한다 (실패 1회, 시도 `1/상한`).
2. **시작 기록.** 코드를 바꾸기 전에 루프 기록(상태 `진행 중`, 시도 `0/상한`)을 남긴다.
   이미 루프 기록이 있으면 새로 시작하지 않고 6절(복구)을 따른다.
3. **구현.**
4. **검증.** `npm run verify`를 실행한다.
5. **시도 기록.** 결과와 상관없이 매 시도 직후 루프 기록을 남긴다.
6. **판정.**
   - exit 0 → 상태 `통과`로 기록하고 루프를 끝낸다.
   - 실패, 시도 < 상한 → 3으로 돌아간다.
   - 실패, 시도 = 상한 → 상한 도달로 `NEEDS_HUMAN`을 선언한다 (5절). 마지막 verify 실패와 같은 시도이므로 추가로 세지 않는다.
7. 루프 중 언제든 5.1절 조건이 생기면 그 자리에서 멈추고 `NEEDS_HUMAN`을 선언한다. 선언은 실패 1회로 센다 (2절).

## 4. 루프 기록 — Issue 코멘트

루프의 상태는 **해당 Issue의 코멘트로만** 남긴다. 대화나 로컬 파일에 남긴 것은 기록으로 치지 않는다.

### 언제 남기는가

| 시점 | 상태 |
|---|---|
| 시작할 때 (코드 변경 전) | `진행 중` |
| 매 시도 직후 | `진행 중` 또는 `통과` |
| 멈출 때 | `NEEDS_HUMAN` |
| 사람의 판단을 받아 다시 시작할 때 | `진행 중` |
| 사람이 중단을 정했을 때 | `중단` |

- 이전 코멘트를 고치지 않는다. 항상 새 코멘트를 덧붙인다.
- 상한은 매 기록에 다시 적는다. 이전 기록을 찾아보지 않아도 남은 횟수를 알 수 있어야 한다.

### 형식

첫 줄의 `<!-- loop-record -->`로 루프 기록을 다른 코멘트와 구분한다.

```markdown
<!-- loop-record -->
**Loop 기록**

- 상태: 진행 중 | 통과 | NEEDS_HUMAN | 중단
- 시도: 2 / 3
- 마지막 검증: exit 1 — 실패 단계 Test
- 실패 요약: issue-3 판정 테스트 "5. 재고 수량 불변" 실패 (기대 54, 실제 50)
- 이번 시도에서 바꾼 것: src/actions/outbound.ts 검사 위치를 applyMovement 앞으로 이동
- 다음 할 일: 3회차 — 수동 선택 경로에도 같은 검사 적용
```

| 필드 | 규칙 |
|---|---|
| 상태 | 위 넷 중 하나 |
| 시도 | `n / 상한`. 시작 기록은 `0 / 상한` |
| 마지막 검증 | exit code와 실패 단계 이름 ([VerifyRule](VerifyRule.md) 1절의 단계명). 시작 기록은 `없음` |
| 실패 요약 | 에러 출력에서 원인이 드러나는 부분. 통과면 생략 |
| 이번 시도에서 바꾼 것 | 파일과 변경 요지 |
| 다음 할 일 | 다음 세션이 그대로 이어받을 수 있는 한 줄 |

## 5. NEEDS_HUMAN

### 5.1 선언하는 경우

| 경우                                       | 근거                             |
| ---------------------------------------- | ------------------------------ |
| Issue와 SSOT(도메인·아키텍처 원본)가 충돌한다           | [SSOT](SSOT.md) 3절             |
| SSOT끼리 충돌한다                              | [SSOT](SSOT.md) 3절             |
| 통과하려면 검증 규칙·스크립트를 바꿔야 한다                 | [VerifyRule](VerifyRule.md) 7절 |
| AI에게 읽기만 허용된 영역을 바꿔야 한다                  | [SSOT](SSOT.md) 4절             |
| Issue만으로 구현 방향을 하나로 정할 수 없다 (업무 판단이 갈린다) | 이 문서                           |
| 상한에 도달했는데 통과하지 못했다                       | 이 문서 3절                        |
| 복구할 때 루프 기록과 작업 트리가 맞지 않는다               | 이 문서 6절                        |

### 5.2 선언할 때 하는 일 — 도움 요청 코멘트

**사람은 이 문서나 양식을 찾아보지 않는다고 가정한다.** 그래서 에이전트는 도움을 요청할 때 사람이 채울 응답 양식(5.3절)을 **요청 안에 직접 붙여서** 준다.

1. **즉시 멈춘다.** 코드를 더 바꾸지 않고, `npm run verify`도 더 돌리지 않는다.
2. 상태 `NEEDS_HUMAN`으로 루프 기록을 남긴다. 기본 필드(4절)에 아래를 덧붙이고, 맨 끝에 **응답 양식**을 붙인다.
   - 응답 양식의 선택지는 이번 사유에 맞게 에이전트가 미리 채운다. 사람은 고르고 붙여 넣기만 하면 된다.
   - 응답 양식은 복사하기 쉽게 코드 블록으로 감싼다.
3. **선언은 실패 1회로 센다.** 시도 횟수를 1 올려 기록한다. 단, 직전 verify 실패를 이유로 곧바로 선언하는 경우(상한 도달 포함)는 그 시도와 같은 실패이므로 올리지 않는다 (2절).
   - 기록한 시도가 상한과 같아 남은 횟수가 없으면, 응답 양식의 `상한` 칸에 새 값을 제안해 미리 채운다.
4. 대화 중이면 사용자에게도 **같은 내용과 같은 응답 양식**을 준다. 사용자는 대화로 답해도 된다 (5.4절).

예시 — 에이전트가 남기는 도움 요청 코멘트:

````markdown
<!-- loop-record -->
**Loop 기록**

- 상태: NEEDS_HUMAN
- 시도: 1 / 3 (NEEDS_HUMAN 선언을 실패 1회로 셈)
- 마지막 검증: 없음
- 사유: Issue ↔ SSOT 충돌
- 근거: Issue #3 "2. 변경할 내용" ↔ docs/06-architecture.md §4.2 "만료된 로트도 후보에 포함한다"
- 선택지:
  1. 출고 요청 전체를 거부한다 (배분 로직은 그대로)
  2. 7일 미만 로트를 배분에서 제외한다 (풀필먼트·팝업과 공유하는 배분 함수를 바꿔야 함)
- 에이전트 의견: 1안 — Issue "5. 건드리면 안 되는 것"과 겹치지 않는다
- 다음 할 일: 사람의 응답을 기다린다

**아래 양식을 복사해 이 Issue에 코멘트로 남겨 주세요.**

```markdown
<!-- loop-decision -->
**NEEDS_HUMAN 응답 (사람 작성)**

- 결정: 1   ← 1 / 2 / 직접 입력
- 상한: 그대로   ← 그대로 / 새 값(예: 5)
- 재개: 재개   ← 재개 / 중단
- 메모:
```
````

### 5.3 사람의 응답 코멘트 (사람이 작성)

**이 코멘트는 사람이 작성한다.** 에이전트의 루프 기록(`<!-- loop-record -->`)과 달리, `NEEDS_HUMAN`에 대한 사람의 판단을 담는 코멘트다.
첫 줄의 `<!-- loop-decision -->`로 사람의 응답을 구분한다.

- 에이전트는 이 코멘트를 스스로 작성하지 않는다. 사람의 판단 없이 응답을 만들어 재개하지 않는다.
- 예외는 하나다. 사람이 양식 없이 답했거나 대화로만 답한 내용을 에이전트가 **옮겨 적는** 경우다 (5.4절). 이때는 메모에 옮겨 적었다는 사실과 원문 위치를 남긴다.

```markdown
<!-- loop-decision -->
**NEEDS_HUMAN 응답 (사람 작성)**

- 결정: (선택지 번호 또는 직접 입력)
- 상한: 그대로 | 새 값
- 재개: 재개 | 중단
- 메모: (선택)
```

| 필드 | 규칙 |
|---|---|
| 결정 | 요청 코멘트의 선택지 번호. 선택지에 없는 판단이면 문장으로 적는다 |
| 상한 | 바꾸지 않으면 `그대로`. 새 값을 적으면 그 값이 새 상한이 된다 (2절) |
| 재개 | `재개`면 에이전트가 이어서 진행한다. `중단`이면 루프를 끝낸다 |
| 메모 | 에이전트가 알아야 할 추가 지시 |

사유별로 에이전트가 미리 채우는 선택지의 기본형:

| 사유 | 기본 선택지 |
|---|---|
| Issue ↔ SSOT, SSOT ↔ SSOT 충돌 | 따를 쪽(각 선택지) / 사람이 원본을 고친 뒤 재개 |
| 검증 규칙·보호 영역을 바꿔야 함 | 사람이 직접 고친 뒤 재개 / 바꾸지 않는 다른 방법을 찾는다 / 중단 |
| Issue만으로 방향을 정할 수 없음 | 에이전트가 찾은 구현 방향들 |
| 상한 도달 | 상한을 올려 재개 / 중단 |
| 복구 불일치 | 현재 작업 트리를 기준으로 이어간다 / 사람이 작업 트리를 정리한 뒤 재개 / 중단 |

### 5.4 재개

- `NEEDS_HUMAN` 기록 **뒤에** `<!-- loop-decision -->` 응답이 있을 때 재개한다.
- 사람이 양식 없이 답한 경우:
  - 판단이 분명하면 에이전트가 그 내용을 응답 양식으로 옮겨 Issue에 남긴 뒤 재개한다. 메모에 `에이전트가 옮겨 적음 — 원문: <코멘트 링크 또는 대화>`를 적는다.
  - 분명하지 않으면 재개하지 않는다. 무엇이 불분명한지 적고 응답 양식을 다시 준다.
- 대화에서만 받은 판단도 같은 방식으로 Issue에 옮겨 적은 뒤 재개한다. Issue에 없는 판단으로는 재개하지 않는다.
- 범위나 종료 조건이 바뀌는 판단이면 Issue 본문을 먼저 고친다 ([SSOT](SSOT.md) 2절).
- 상한을 바꾼 응답이면 그 값을 새 상한으로 쓴다. 시도 횟수는 0으로 되돌리지 않고 이어서 센다.
- 재개할 때 남은 횟수가 없으면(시도 = 상한) 응답에서 상한을 올려야 재개한다. 상한이 `그대로`면 재개하지 않고, 상한을 올려 달라고 응답 양식을 다시 준다.
- `재개`면 상태 `진행 중`으로 루프 기록을 남기고, 근거가 된 응답을 적는다.
- `중단`이면 상태 `중단`으로 루프 기록을 남기고 끝낸다.

## 6. 세션이 바뀌었을 때 복구

새 세션은 작업을 시작하기 전에 다음을 한다.

1. Issue 본문과 코멘트를 읽는다 — `gh issue view <번호> --repo jo-narae/inventory-harness-lab-1124 --comments`
2. `<!-- loop-record -->`가 있는 코멘트 중 **가장 최근 것**을 현재 상태로 삼는다. 그 뒤에 달린 `<!-- loop-decision -->` 응답도 함께 읽는다.

| 현재 상태 | 할 일 |
|---|---|
| 기록 없음 | 처음부터 시작한다 (3절 1단계) |
| `진행 중` | 기록된 시도 횟수에서 이어간다. "다음 할 일"부터 시작한다 |
| `NEEDS_HUMAN` | 그 뒤에 사람의 응답이 Issue에 있으면 5.4절대로 재개한다. 없으면 아무것도 하지 않고, 대기 중이라는 사실과 응답 양식을 사용자에게 다시 준다 |
| `통과` | 루프를 다시 돌리지 않는다. 이미 통과했다고 알린다 |
| `중단` | 루프를 다시 돌리지 않는다. 사람이 중단했다고 알린다 |

3. 작업 트리를 확인한다. 루프 기록의 "이번 시도에서 바꾼 것"과 작업 트리가 맞지 않으면 추측해서 맞추지 않는다. `NEEDS_HUMAN`(복구 불일치)을 선언한다.

- 시도 횟수는 세션이 바뀌어도 초기화하지 않는다. Issue에 남은 기록이 유일한 근거다.
- 루프 기록 없이 진행한 시도는 복구할 수 없다. 그래서 4절의 "매 시도 직후 기록"을 건너뛰지 않는다.
