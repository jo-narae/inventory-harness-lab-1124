# Loop — 루프 규칙

Issue 작업 하나를 **시작해서 CI를 통과하거나 멈출 때까지** 에이전트가 따르는 절차를 정한다.
세션이 끊기거나 바뀌어도 같은 지점에서 이어갈 수 있게 하는 것이 목적이다.

---

## 1. 범위

| 다룬다 | 다루지 않는다 (이 문서 밖) |
|---|---|
| 작업 시작 점검 | 머지 (사람이 한다) |
| 시도 횟수와 상한 | `main`과의 충돌 해소 |
| Issue 코멘트로 남기는 루프 기록 | 머지 뒤 `main` push CI |
| `NEEDS_HUMAN` 선언, 사람의 응답 양식, 재개 | Issue 닫기, 종료 조건 체크박스 처리 |
| 브랜치 · 커밋 · 푸시 · PR 생성 (최소 규칙, 6.1절) | 판정 테스트의 승인 · 보호 절차 |
| PR · CI 진입과 복귀, PR 리뷰 변경 요청 | 작업 공간 정리 |
| 세션이 바뀌었을 때 복구 | |

통과 기준과 검증 단계, CI가 무엇을 실행하는지는 [`VerifyRule.md`](VerifyRule.md)를 따른다. 이 문서는 그 기준을 **몇 번까지, 어떻게 기록하며** 돌리는지와 **언제 PR · CI로 넘어가고 돌아오는지**만 정한다.

브랜치 규칙은 당분간 이 문서에 둔다. 문서가 복잡해지면 별도 SSOT로 나눈다.

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 시도 | 아래 "시도로 세는 것" 표에서 **+1**로 정한 사건 |
| 상한 | 해당 Issue "6. 구현 루프 최대 횟수"의 값. 사람이 응답(5.3절)에서 상한을 바꿨으면 가장 최근 응답의 값. **로컬 검증과 CI가 함께 쓴다** |
| 재작업 | PR 리뷰의 변경 요청을 Issue에 반영한 뒤 다시 구현에 들어가는 것 (6.5절) |
| 재진입 | 멈췄던 루프를 이어가는 것. `NEEDS_HUMAN` 응답을 받아 **재개**하거나, 세션이 바뀌어 **복구**하는 것 |
| 루프 기록 | 에이전트가 Issue에 남기는 코멘트 (4절 형식) |
| 현재 상태 | 그 Issue의 **가장 최근** 루프 기록 |

### 상태

| 상태 | 뜻 |
|---|---|
| `진행 중` | 로컬 루프에서 구현 · 검증 중 |
| `로컬 통과` | 로컬 `npm run verify` exit 0. PR을 누가 열지 응답을 기다린다 (6.2절) |
| `CI 대기` | PR의 CI 결과를 기다린다 (6.3절) |
| `CI 통과` | PR의 CI가 통과했다. 루프가 끝나고 머지를 기다린다 |
| `NEEDS_HUMAN` | 사람의 판단을 기다린다 (5절) |
| `중단` | 사람이 중단을 정했다 |

### 시도로 세는 것 / 세지 않는 것

**`NEEDS_HUMAN` 선언 자체는 세지 않는다.** 선언의 원인이 되는 사건만 센다. `NEEDS_HUMAN`이 원인일 때의 셈은 5.1절 표를 따른다.

| 사건 | 셈 |
|---|---|
| 로컬에서 `npm run verify`가 끝나고 exit code를 확인했다 (0이든 아니든) | **+1** |
| PR의 CI가 실패했다 | **+1** |
| PR 리뷰 변경 요청으로 재작업에 들어갔다 (6.5절) | **+1** |
| 루프 중에 판단형 `NEEDS_HUMAN` 사유가 생겼다 (5.1절) | **+1** |
| 시작 점검에서 판단형 `NEEDS_HUMAN` 사유가 생겼다 | 0 |
| 실패형 `NEEDS_HUMAN`을 선언했다 (상한 도달, CI 실패) | 0 — 원인이 된 실패를 이미 셌다 |
| 재진입했다 (재개, 복구) | 0 |
| 복구할 때 기록이 맞지 않아 `NEEDS_HUMAN`을 선언했다 | 0 — 재진입 시점이다 |
| PR 진입 응답을 요청했다, CI가 통과했다 | 0 |
| 단계 하나만 따로 실행했다 (`vitest run`, `npm run lint` 등) | 0. 판정에도 쓰지 않는다 |
| 명령을 잘못 써서, 또는 중간에 끊겨서 exit code를 확인하지 못했다 | 0. 다시 실행한다 |

## 3. 루프 절차

```
시작 점검 ──걸림──▶ NEEDS_HUMAN (0)
    │ 통과
    ▼
브랜치 ─▶ 시작 기록 ─▶ ┌──────────── 로컬 루프 ────────────┐
                       │ 구현 ─▶ npm run verify ─▶ 시도 기록(+1)
                       │  ▲                          │
                       │  └──── 실패, n < 상한 ──────┤
                       └─────────────────────────────┼──────┘
                                                     ├─ 실패, n = 상한 ─▶ NEEDS_HUMAN (0, 상한 도달)
                                                     ▼ exit 0
                                                 로컬 통과 ─▶ PR 진입 응답 (AI / 사람)
                                                                 │
                                                                 ▼
                                                             CI 대기
                                                   ┌─────────────┴─────────────┐
                                             CI 실패(+1)                   CI 통과 (루프 종료)
                                                   │                           │
                                                   ▼                           │
                                       NEEDS_HUMAN (0, CI 실패)                │
                                                                               │
              구현으로 복귀 ◀── 재작업(+1) ◀── PR 리뷰 변경 요청 (CI 대기 · CI 통과 중) ◀┘
```

1. **시작 점검.** Issue당 **처음 한 번만** 한다 (루프 기록이 없을 때). Issue를 읽고 5.1절의 판단형 사유에 해당하는지 본다. 해당하면 구현하지 않고 `NEEDS_HUMAN`을 선언한다. 시작 점검에서는 세지 않는다 (`0/상한`).
   - 재진입(재개 · 복구)과 재작업 때는 시작 점검을 다시 하지 않는다.
2. **브랜치.** 6.1절대로 작업 브랜치를 만든다.
3. **시작 기록.** 코드를 바꾸기 전에 루프 기록(상태 `진행 중`, 시도 `0/상한`)을 남긴다.
   이미 루프 기록이 있으면 새로 시작하지 않고 7절(복구)을 따른다.
4. **구현.**
5. **검증.** `npm run verify`를 실행한다.
6. **시도 기록.** 결과와 상관없이 매 시도 직후 루프 기록을 남긴다 (+1).
7. **판정.**
   - exit 0 → 상태 `로컬 통과`로 기록하고 PR 진입 응답을 요청한다 (6.2절).
   - 실패, 시도 < 상한 → 4로 돌아간다.
   - 실패, 시도 = 상한 → 상한 도달로 `NEEDS_HUMAN`을 선언한다 (실패형, 0).
8. 루프 중 언제든 5.1절의 판단형 사유가 생기면 그 자리에서 멈추고 `NEEDS_HUMAN`을 선언한다 (+1).

**PR · CI로는 로컬 `npm run verify`가 exit 0일 때만 들어간다.** 로컬에서 통과하지 않은 코드를 커밋 · 푸시해 CI로 확인하지 않는다.

## 4. 루프 기록 — Issue 코멘트

루프의 상태는 **해당 Issue의 코멘트로만** 남긴다. 대화나 로컬 파일에 남긴 것은 기록으로 치지 않는다.

### 언제 남기는가

| 시점 | 상태 |
|---|---|
| 시작할 때 (코드 변경 전) | `진행 중` |
| 매 로컬 시도 직후 | `진행 중` 또는 `로컬 통과` |
| PR이 생기고 CI가 시작됐을 때 (재푸시 포함) | `CI 대기` |
| CI 결과를 확인했을 때 | `CI 통과` 또는 `NEEDS_HUMAN` |
| 재작업에 들어갈 때 | `진행 중` |
| 멈출 때 | `NEEDS_HUMAN` |
| 사람의 판단을 받아 다시 시작할 때 | `진행 중` |
| 사람이 중단을 정했을 때 | `중단` |

- 이전 코멘트를 고치지 않는다. 항상 새 코멘트를 덧붙인다.
- 상한은 매 기록에 다시 적는다. 이전 기록을 찾아보지 않아도 남은 횟수를 알 수 있어야 한다.

### 형식

첫 줄의 `<!-- loop-record -->`로 루프 기록을 다른 코멘트와 구분한다.

```markdown
<!-- loop-record -->
**Loop 기록**

- 상태: CI 대기
- 시도: 2 / 3
- 마지막 검증: 로컬 exit 0
- 이번 시도에서 바꾼 것: src/actions/outbound.ts 검사 위치를 applyMovement 앞으로 이동
- 브랜치: issue-3-expired-product-outbound
- PR: #7
- 커밋: 3f5aefd
- CI: https://github.com/<owner>/<repo>/actions/runs/<id>
- 다음 할 일: CI 결과 확인
```

| 필드 | 규칙 |
|---|---|
| 상태 | 2절 상태 중 하나 |
| 시도 | `n / 상한`. 시작 기록은 `0 / 상한` |
| 마지막 검증 | 어디서(로컬 · CI) 돌렸는지, exit code, 실패 단계 이름 ([VerifyRule](VerifyRule.md) 1절의 단계명). 시작 기록은 `없음` |
| 실패 요약 | 에러 출력에서 원인이 드러나는 부분. 통과면 생략 |
| 이번 시도에서 바꾼 것 | 파일과 변경 요지 |
| 브랜치 | 작업 브랜치 이름 (6.1절) |
| PR | PR 번호. PR이 생긴 뒤부터 적는다 |
| 커밋 | PR의 최신 커밋 SHA. 푸시한 뒤부터 적는다 |
| CI | CI 실행 링크. CI가 시작된 뒤부터 적는다 |
| 다음 할 일 | 다음 세션이 그대로 이어받을 수 있는 한 줄 |

## 5. NEEDS_HUMAN

### 5.1 선언하는 경우와 셈

`NEEDS_HUMAN`은 두 종류다.

- **판단형** — Issue나 원본 문서만으로는 에이전트가 정할 수 없어 사람의 판단이 필요한 경우.
- **실패형** — 실패가 쌓였거나 원인을 알 수 없는 실패가 나서 멈추는 경우. 원인이 된 실패는 그 자체로 이미 셌다.

| 경우 | 분류 | 셈 | 근거 |
|---|---|---|---|
| Issue와 SSOT(도메인·아키텍처 원본)가 충돌한다 | 판단형 | 루프 중 +1 · 시작 점검 0 | [SSOT](SSOT.md) 3절 |
| SSOT끼리 충돌한다 | 판단형 | 루프 중 +1 · 시작 점검 0 | [SSOT](SSOT.md) 3절 |
| 통과하려면 검증 규칙·스크립트를 바꿔야 한다 | 판단형 | 루프 중 +1 · 시작 점검 0 | [VerifyRule](VerifyRule.md) 7절 |
| AI에게 읽기만 허용된 영역을 바꿔야 한다 | 판단형 | 루프 중 +1 · 시작 점검 0 | [SSOT](SSOT.md) 4절 |
| Issue만으로 구현 방향을 하나로 정할 수 없다 (업무 판단이 갈린다) | 판단형 | 루프 중 +1 · 시작 점검 0 | 이 문서 |
| 복구할 때 루프 기록과 작업 트리 · 브랜치 · PR이 맞지 않는다 | 판단형 | 0 (재진입 시점) | 이 문서 7절 |
| 상한에 도달했는데 통과하지 못했다 | 실패형 | 0 | 이 문서 3절 · 6.5절 |
| 로컬에서 통과한 커밋이 CI에서 실패했다 | 실패형 | 0 (CI 실패로 이미 +1) | 이 문서 6.4절 |

### 5.2 선언할 때 하는 일 — 도움 요청 코멘트

**사람은 이 문서나 양식을 찾아보지 않는다고 가정한다.** 그래서 에이전트는 도움을 요청할 때 사람이 채울 응답 양식(5.3절)을 **요청 안에 직접 붙여서** 준다.

1. **즉시 멈춘다.** 코드를 더 바꾸지 않고, `npm run verify`도 더 돌리지 않고, 커밋 · 푸시도 하지 않는다.
2. 상태 `NEEDS_HUMAN`으로 루프 기록을 남긴다. 기본 필드(4절)에 아래를 덧붙이고, 맨 끝에 **응답 양식**을 붙인다.
   - 응답 양식의 선택지는 이번 사유에 맞게 에이전트가 미리 채운다. 사람은 고르고 붙여 넣기만 하면 된다.
   - 응답 양식은 복사하기 쉽게 코드 블록으로 감싼다.
3. **시도 횟수는 5.1절 표의 셈대로 기록한다.** 선언 자체로는 올리지 않는다.
   - 기록한 시도가 상한과 같아 남은 횟수가 없으면, 응답 양식의 `상한` 칸에 새 값을 제안해 미리 채운다.
4. 대화 중이면 사용자에게도 **같은 내용과 같은 응답 양식**을 준다. 사용자는 대화로 답해도 된다 (5.4절).

예시 — 시작 점검에서 남기는 도움 요청 코멘트:

````markdown
<!-- loop-record -->
**Loop 기록**

- 상태: NEEDS_HUMAN
- 시도: 0 / 3 (시작 점검이라 세지 않음)
- 마지막 검증: 없음
- 분류: 판단형
- 사유: Issue ↔ SSOT 충돌
- 근거: Issue #3 "2. 변경할 내용" ↔ docs/06-architecture.md §4.2 "만료된 로트도 후보에 포함한다"
- 선택지:
  1. 출고 요청 전체를 거부한다 (배분 로직은 그대로)
  2. 7일 미만 로트를 배분에서 제외한다 (풀필먼트·팝업과 공유하는 배분 함수를 바꿔야 함)
- 에이전트 의견: 1안 — Issue "5. 건드리면 안 되는 것"과 겹치지 않는다
- 다음 할 일: 사람의 응답을 기다린다

**아래 양식을 복사해 이 Issue에 코멘트로 남겨 주세요.**

```markdown
<!-- loop-decision -->
**NEEDS_HUMAN 응답 (사람 작성)**

- 결정: 1   ← 1 / 2 / 직접 입력
- 상한: 그대로   ← 그대로 / 새 값(예: 5)
- 재개: 재개   ← 재개 / 중단
- 메모:
```
````

### 5.3 사람의 응답 코멘트 (사람이 작성)

**이 코멘트는 사람이 작성한다.** 에이전트의 루프 기록(`<!-- loop-record -->`)과 달리, 에이전트가 요청한 판단에 대한 사람의 답을 담는 코멘트다.
첫 줄의 `<!-- loop-decision -->`로 사람의 응답을 구분한다. 응답 양식은 두 가지다.

| 양식 | 쓰는 곳 |
|---|---|
| NEEDS_HUMAN 응답 | `NEEDS_HUMAN`에 답할 때 (아래) |
| PR 진입 응답 | `로컬 통과`에서 PR을 누가 열지 답할 때 (6.2절) |

- 에이전트는 이 코멘트를 스스로 작성하지 않는다. 사람의 판단 없이 응답을 만들어 진행하지 않는다.
- 예외는 하나다. 사람이 양식 없이 답했거나, 대화 · PR 리뷰로만 답한 내용을 에이전트가 **옮겨 적는** 경우다 (5.4절, 6.5절). 이때는 메모에 옮겨 적었다는 사실과 원문 위치를 남긴다.

**NEEDS_HUMAN 응답 양식**

```markdown
<!-- loop-decision -->
**NEEDS_HUMAN 응답 (사람 작성)**

- 결정: (선택지 번호 또는 직접 입력)
- 상한: 그대로 | 새 값
- 재개: 재개 | 중단
- 메모: (선택)
```

| 필드 | 규칙 |
|---|---|
| 결정 | 요청 코멘트의 선택지 번호. 선택지에 없는 판단이면 문장으로 적는다 |
| 상한 | 바꾸지 않으면 `그대로`. 새 값을 적으면 그 값이 새 상한이 된다 (2절) |
| 재개 | `재개`면 에이전트가 이어서 진행한다. `중단`이면 루프를 끝낸다 |
| 메모 | 에이전트가 알아야 할 추가 지시 |

사유별로 에이전트가 미리 채우는 선택지의 기본형:

| 사유 | 기본 선택지 |
|---|---|
| Issue ↔ SSOT, SSOT ↔ SSOT 충돌 | 따를 쪽(각 선택지) / 사람이 원본을 고친 뒤 재개 |
| 검증 규칙·보호 영역을 바꿔야 함 | 사람이 직접 고친 뒤 재개 / 바꾸지 않는 다른 방법을 찾는다 / 중단 |
| Issue만으로 방향을 정할 수 없음 | 에이전트가 찾은 구현 방향들 |
| 복구 불일치 | 현재 작업 트리 · 브랜치를 기준으로 이어간다 / 사람이 정리한 뒤 재개 / 중단 |
| 상한 도달 | 상한을 올려 재개 / 중단 |
| CI 실패 (로컬은 통과) | 사람이 원인을 고친 뒤 CI를 다시 확인 / 재작업 지시 (Issue에 반영) / 중단 |

### 5.4 재개

- `NEEDS_HUMAN` 기록 **뒤에** NEEDS_HUMAN 응답이 있을 때 재개한다.
- 사람이 양식 없이 답한 경우:
  - 판단이 분명하면 에이전트가 그 내용을 응답 양식으로 옮겨 Issue에 남긴 뒤 재개한다. 메모에 `에이전트가 옮겨 적음 — 원문: <코멘트 링크 또는 대화>`를 적는다.
  - 분명하지 않으면 재개하지 않는다. 무엇이 불분명한지 적고 응답 양식을 다시 준다.
- 대화에서만 받은 판단도 같은 방식으로 Issue에 옮겨 적은 뒤 재개한다. Issue에 없는 판단으로는 재개하지 않는다.
- 범위나 종료 조건이 바뀌는 판단이면 Issue 본문을 먼저 고친다 ([SSOT](SSOT.md) 2절).
- 상한을 바꾼 응답이면 그 값을 새 상한으로 쓴다. 시도 횟수는 0으로 되돌리지 않고 이어서 센다.
- 재개할 때 남은 횟수가 없으면(시도 = 상한) 응답에서 상한을 올려야 재개한다. 상한이 `그대로`면 재개하지 않고, 상한을 올려 달라고 응답 양식을 다시 준다.
- **재개는 재진입이다.** 시작 점검을 다시 하지 않고, 시도로 세지 않는다.
- `재개`면 상태 `진행 중`으로 루프 기록을 남기고, 근거가 된 응답을 적는다.
- `중단`이면 상태 `중단`으로 루프 기록을 남기고 끝낸다.

## 6. PR · CI

### 6.1 브랜치 · 커밋 · 푸시 (최소 규칙)

| 항목 | 규칙 |
|---|---|
| 브랜치 이름 | `issue-{Issue 번호}-{기능명}`. 기능명은 판정 테스트 파일(`tests/issues/issue-{번호}-{기능명}.test.ts`)과 같게 쓴다 |
| 만드는 시점 | 시작 기록 전, 코드를 바꾸기 전. 최신 `main`에서 만든다 |
| 이미 있으면 | 새로 만들지 않고 그 브랜치에서 이어간다 (7절) |
| 작업 위치 | `main`에서 직접 작업 · 커밋 · 푸시하지 않는다 |
| 커밋 · 푸시 시점 | `로컬 통과` 상태에서만. 처음 PR은 6.2절 응답대로, PR이 생긴 뒤의 재푸시는 응답 없이 에이전트가 한다 |
| PR | base `main`, 제목은 Issue 제목, 본문에 `Refs #{Issue 번호}`. `Closes` · `Fixes`는 쓰지 않는다 (Issue 닫기는 범위 밖) |
| 하지 않는 것 | force push, 푸시한 커밋 고쳐 쓰기(amend · rebase), 머지, PR 닫기 |

### 6.2 PR 진입 — 누가 PR을 여는가

이 단계에서 사람이 정하는 것은 **PR을 에이전트가 열지, 사람이 직접 열지**뿐이다. 수정 요청은 PR이 생긴 뒤 리뷰로 받는다 (6.5절).

1. 로컬 `npm run verify`가 exit 0이면 상태 `로컬 통과`로 루프 기록을 남기고 멈춘다.
2. 그 기록 끝에 아래 **PR 진입 응답** 양식을 붙여 요청한다. 대화 중이면 사용자에게도 같은 양식을 준다.

```markdown
<!-- loop-decision -->
**PR 진입 응답 (사람 작성)**

- 진행: AI   ← AI / 사람
- 메모:
```

3. 응답에 따라:
   - **AI** → 에이전트가 커밋 · 푸시 · PR 생성 (6.1절) → 상태 `CI 대기`로 기록한다.
   - **사람** → 사람이 직접 커밋 · 푸시 · PR을 만든다. 에이전트는 그 브랜치에 PR이 생겼는지(`gh pr list --head <브랜치>`) 확인한 뒤 PR 번호 · 커밋 SHA를 적어 `CI 대기`로 기록한다.
- 이 요청은 `NEEDS_HUMAN`이 아니다. 시도로 세지 않는다.
- PR이 이미 있는 상태에서 다시 `로컬 통과`가 되면 응답을 요청하지 않는다. 에이전트가 같은 브랜치에 커밋 · 푸시하고 `CI 대기`로 기록한다.

### 6.3 CI 대기

- `CI 대기`로 기록할 때 PR 번호, PR의 최신 커밋 SHA, CI 실행 링크를 적는다.
- 세션 안에서는 `gh pr checks <PR 번호> --watch`로 결과를 기다린다.
- 세션이 끝나도 괜찮다. 다음 세션이 7절대로 CI 결과를 확인해 이어간다.
- CI 결과는 **기록한 커밋 SHA에 대한 것**만 인정한다. PR의 최신 커밋(`gh pr view <PR 번호> --json headRefOid`)이 기록과 다르면 복구 불일치로 본다 (7절).

### 6.4 CI 결과와 복귀

| 결과 | 셈 | 처리 |
|---|---|---|
| CI 통과 | 0 | 상태 `CI 통과`로 기록한다. **루프가 끝난다.** 머지는 사람이 한다 |
| CI 실패 | **+1** | 실패형 `NEEDS_HUMAN`(CI 실패)을 선언한다 (선언은 0). 실패 단계와 CI 로그 요약을 적는다 |

- 로컬에서 통과한 커밋만 CI로 가므로, CI 실패는 로컬과 CI의 차이로 본다. 에이전트는 원인을 추측해서 고치지 않고 사람에게 판단을 요청한다. CI 워크플로는 보호 영역이다 ([VerifyRule](VerifyRule.md) 7절).
- CI 실패로 상한에 닿아도 처리는 같다. 응답 양식의 `상한` 칸에 새 값을 제안해 채운다 (5.2절).

### 6.5 PR 리뷰 변경 요청 — 재작업

PR 리뷰의 변경 요청(GitHub "Request changes" 리뷰, 또는 사람이 변경을 요청한 PR 코멘트)은 **재작업**이다. `CI 대기` 중이든, `CI 통과`로 루프가 끝난 뒤든 같다.

1. 변경 요청을 Issue에 반영한다.
   - 범위나 종료 조건이 바뀌면 Issue 본문을 먼저 고친다 ([SSOT](SSOT.md) 2절).
   - PR 리뷰에만 있는 요청은 에이전트가 응답 양식으로 옮겨 Issue에 남긴다. 메모에 `에이전트가 옮겨 적음 — 원문: <PR 리뷰 링크>`를 적는다.
2. **시도를 1 올려** 상태 `진행 중`으로 루프 기록을 남긴다. 어떤 요청으로 재작업하는지 적는다.
3. 같은 브랜치에서 로컬 루프로 돌아간다 (3절 4단계). 시작 점검은 다시 하지 않는다. 다시 `로컬 통과`가 되면 6.2절 마지막 항목대로 재푸시한다.

- 재작업으로 시도가 상한에 닿으면 로컬 검증을 할 수 없다. 곧바로 실패형 `NEEDS_HUMAN`(상한 도달)을 선언한다 (0).

## 7. 세션이 바뀌었을 때 복구

복구는 재진입이다. 시작 점검을 다시 하지 않고, 시도로 세지 않는다.

1. Issue 본문과 코멘트를 읽는다 — `gh issue view <번호> --repo jo-narae/inventory-harness-lab-1124 --comments`
2. `<!-- loop-record -->`가 있는 코멘트 중 **가장 최근 것**을 현재 상태로 삼는다. 그 뒤에 달린 `<!-- loop-decision -->` 응답도 함께 읽는다.
3. 기록에 PR이 있으면 PR의 리뷰와 코멘트, CI 결과도 읽는다 — `gh pr view <PR 번호> --comments`, `gh pr checks <PR 번호>`

| 현재 상태 | 할 일 |
|---|---|
| 기록 없음 | 처음부터 시작한다 (3절 1단계) |
| `진행 중` | 기록된 시도 횟수에서 이어간다. "다음 할 일"부터 시작한다 |
| `로컬 통과` | PR 진입 응답이 있으면 6.2절대로 진행한다. `사람`이면 그 브랜치에 PR이 생겼는지 확인한다. 응답이 없으면 대기 중이라는 사실과 응답 양식을 사용자에게 다시 준다 |
| `CI 대기` | CI 결과를 확인해 6.4절대로 처리한다. 아직 돌고 있으면 기다린다. 리뷰 변경 요청이 있으면 6.5절 |
| `CI 통과` | 루프를 다시 돌리지 않는다. 그 뒤에 리뷰 변경 요청이 있으면 6.5절대로 재작업한다. 없으면 머지 대기라고 알린다 |
| `NEEDS_HUMAN` | 그 뒤에 사람의 응답이 Issue에 있으면 5.4절대로 재개한다. 없으면 아무것도 하지 않고, 대기 중이라는 사실과 응답 양식을 사용자에게 다시 준다 |
| `중단` | 루프를 다시 돌리지 않는다. 사람이 중단했다고 알린다 |

4. 작업 위치를 확인한다. 기록에 브랜치가 있으면 그 브랜치로 전환한다. 아래 중 하나라도 맞지 않으면 추측해서 맞추지 않고 `NEEDS_HUMAN`(복구 불일치)을 선언한다. 재진입 시점이므로 세지 않는다 (0).
   - 기록의 브랜치가 없다
   - 작업 트리가 기록의 "이번 시도에서 바꾼 것"과 맞지 않는다
   - 기록에 커밋이 있는데 브랜치 · PR의 최신 커밋이 그것과 다르다

- 시도 횟수는 세션이 바뀌어도 초기화하지 않는다. Issue에 남은 기록이 유일한 근거다.
- 루프 기록 없이 진행한 시도는 복구할 수 없다. 그래서 4절의 "언제 남기는가"를 건너뛰지 않는다.
